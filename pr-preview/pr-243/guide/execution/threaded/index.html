      Execution
      Run threaded host kernels

      Run threaded host kernels

      Run independent particle rows in concurrent host chunks, then compare their results with sequential execution. Start with systems and kernel access. Threading is experimental; it changes invocation boundaries within one kernel call, while systems still run in registration order.

      Keep inputs portable and work independent

      The stage uses plain components and explicitly read-only time.

      @fieldwise_init
struct Position(Copyable, Movable, TrivialRegisterPassable):
    """Particle coordinates, using device-compatible scalar arithmetic."""

    var x: Float32
    var y: Float32


@fieldwise_init
struct Velocity(Copyable, Movable, TrivialRegisterPassable):
    """Particle displacement per unit of simulated time."""

    var dx: Float32
    var dy: Float32


@fieldwise_init
struct Time(Copyable, Movable):
    """Shared simulated step length."""

    var delta: Float32

      The component fields contain only scalar values. Threaded eligibility checks pointer-free trivial representation for accessed components; a device component trait alone does not establish this. Unaccessed owning components can coexist in the world.

      The movement loop changes only its own row.

      comptime move_filter = Filter().include[Position]().read[Velocity]()
comptime move_resources = Resources().read[Time]()


def move(context: KernelContext[move_filter, move_resources]):
    """Moves each row using its velocity and the shared step length.

    Args:
        context: Matching rows and read-only time.
    """
    ref time = context.resources.get[Time]()
    for particle in context:
        ref position = particle.get[Position]()
        ref velocity = particle.get[Velocity]()
        position.x += velocity.dx * time.delta
        position.y += velocity.dy * time.delta

      Resources().read[Time]() shares one immutable time value with every chunk. Ordinary mutable resources, including the Resources[Time]() read-write default, are rejected even when a configuration uses sequential fallback. Adapter views can expose owning read inputs.

      Opt in per invocation; configuring the world alone does not enable threading.

      @fieldwise_init
struct Move[threaded: Bool](System):
    """Opts into host chunks for this movement kernel."""

    def update(mut self, mut context: SystemContext[...]) raises:
        """Moves disjoint rows and joins before returning.

        Args:
            context: Access to the simulation world.

        Raises:
            Error: If threaded eligibility or preparation fails.
        """
        context.run[move, threaded=Self.threaded]()

      context.run[move, threaded=True]() requires a nonraising thin kernel and HOST. Lexical closures, explicit captures, and threaded=True with DEVICE fail at compile time. EntitySelection.run supports the same threaded engine on exact selected ranges.

      Configure and check the result

      This driver compares ordinary sequential execution, one-worker fallback, and a four-task configuration, each from a fresh world.

      def run_stage[threaded: Bool](workers: Int) raises -> Position:
    """Checks parallel dispatch and whole-range fallback against exact values.

    Parameters:
        threaded: Whether to opt into the threaded engine.

    Args:
        workers: Submitted task budget; one exercises sequential fallback.

    Raises:
        Error: If configuration, execution, or a result check fails.

    Returns:
        Coordinate sums after two steps.
    """
    var world = World[Position, Velocity](
        execution_config=ThreadedExecutionConfig(
            workers=workers, chunks_per_worker=2, min_parallel_rows=0
        )
    )
    world.resources.add(Time(0.25))
    _ = world.storage.add_entities(Position(0, 0), Velocity(1, 2), count=4097)
    var scheduler = Scheduler[Position, Velocity](world^)
    scheduler.add_system(Move[threaded]())
    scheduler.run(steps=2)
    var total = Position(0, 0)
    for particle in scheduler.world.storage.query[move_filter]():
        ref position = particle.get[Position]()
        assert_almost_equal(position.x, 0.5)
        assert_almost_equal(position.y, 1.0)
        total.x += position.x
        total.y += position.y
    return total


def main() raises:
    """Compares the sequential, one-worker, and multi-task call paths.

    Raises:
        Error: If an execution path disagrees.
    """
    var sequential = run_stage[False](1)
    var fallback = run_stage[True](1)
    var threaded = run_stage[True](4)
    assert_equal(fallback.x, sequential.x)
    assert_equal(fallback.y, sequential.y)
    assert_equal(threaded.x, sequential.x)
    assert_equal(threaded.y, sequential.y)
    print(
        "PASS: sequential, one-worker fallback, and four-task particle parity"
    )

      ThreadedExecutionConfig sets a submitted-task budget, not reserved cores or guaranteed OS thread overlap. min_parallel_rows=0 disables the size cutoff so the four-task case takes the chunk-dispatch path. All 4097 rows must end at (0.5, 1.0); the uneven count also exercises final short chunks. This result check alone does not prove simultaneous worker overlap.

      From the repository root, run:

      pixi run mojo run -I src examples/particles/threaded.mojo

      The PASS line confirms parity for all three call paths. Hardware concurrency claims need separate worker-overlap evidence, such as the repository’s threaded correctness tests.

      Respect chunk boundaries and lifetimes

      Parallel dispatch splits each physical store or selected range independently. Workers claim disjoint chunks dynamically; invocation order is unspecified. Code outside the row loop runs once per chunk. A row’s idx starts at zero in each host context, including each chunk: do not index a shared global output with it or treat it as an entity ID. KernelContext.thread_count remains one inside a host chunk. Cross-chunk dependencies need a later run after the join.

      Default settings are one worker, four target chunks per worker, and a 65,536 matched-row cutoff. One worker or fewer rows than the cutoff preserves whole-range sequential calls, after all threaded eligibility checks. Empty matches invoke no kernel. Worker/chunk counts must be positive, their product representable, and the cutoff nonnegative.

      Every explicitly threaded run acquires an extra structural lock, even for fallback and an already locked selection. Lock exhaustion raises before work starts. All fallible preparation precedes row writes, and all workers join before the call returns. Fatal worker/runtime failures offer no rollback.

      Keep one coordinating caller for the world. Structural locks and resource leases are not mutexes for external aliases. Do not reenter execution, mutate backing resources, or resize/relocate storage through escaped aliases while workers run; copying, moving, replacing, or destroying an active world aborts. Avoid mutable globals and callees with hidden unsafe mutation.

      Troubleshooting

      Failure or restriction Fix
      Plain-value check fails Remove pointers/ownership from accessed components or ordinary read resources. PlainValue may declare opaque scalar-only StaticTuple/InlineArray fields; the author guarantees the entire representation is pointer-free and trivial.
      Mutable ordinary resource rejected Use explicit read, per-row component outputs, or an adapter declaring both mutation capabilities. A mutable adapter’s concurrent-write contract remains your responsibility.
      Small workload shows no improvement Measure dispatch overhead and complete steps; adjust the cutoff only after profiling.
      Structural lock exhaustion or locked world Release unrelated queries/selections before running or maintaining storage. Empty/exhausted cursors can still own locks.

      See the execution mapping, shared-write alternatives, and complete-step measurement.
