Coordinate shared writes

Compute one shared result, the total displacement of all particles, without a data race. Each particle writes its own output in the kernel, and one caller sums the outputs after run returns. This works on every target, including threaded chunks and device threads, where many invocations run at once. For data you own outside the world, Larecs also provides standalone atomic values and guarded values.

Start with Update entities with systems and kernels. Larecs does not bind synchronization primitives to kernels automatically; see compatibility and status.

Write a separate output for each particle

Section titled “Write a separate output for each particle”

The stage uses the portable particle model and adds a Displacement component that belongs to each particle.

write[Displacement]() grants set-only access, so the kernel must set the output on every row it visits. No two rows share an output, so the kernel needs no synchronization on any target. A resource or a mutable capture slot, by contrast, is one value that every invocation would write.

Variations

Section titled “Variations”

Reduce in several passes

Section titled “Reduce in several passes”

For a parallel reduction, write partial results to disjoint per-particle or per-group components, then combine them in a later run or on the host. Each pass reads only output that an earlier, finished call wrote.

Use a single writer

Section titled “Use a single writer”

One designated writer may update a shared value when it does not need other threads’ unfinished results, as the capture count does with global thread zero. A thread-zero branch is not a barrier.

Update data you own with atomic or guarded values

Section titled “Update data you own with atomic or guarded values”

These primitives work on storage you own, outside the world:

  • AtomicValue owns a UInt32 or Int32 scalar, and AtomicView borrows it. fetch_add returns the previous value. compare_exchange reports whether it exchanged and which value it observed. Operations use relaxed ordering unless you pass an ordering, such as store[Ordering.RELEASE] and load[Ordering.ACQUIRE], at compile time.
  • Synchronized owns guarded data, and SyncView borrows it. try_read and try_write make one attempt and never wait. Check is_acquired before you consume the attempt with take. Several readers may hold the value at once; a writer excludes everyone else. The guard releases at scope exit or through release.

A false is_acquired means Busy: the single attempt met a conflicting guard, a state that changed during the attempt, or the maximum reader count. Larecs does not retry. Record the unfinished work for a later pass, or skip the update only if your application can lose it.

Failures and limits

Section titled “Failures and limits”
Failure Cause and fix
Wrong totals from a shared resource or capture Several invocations wrote one value. Write per-particle output and reduce after run.
try_read or try_write returns Busy The attempt met a conflicting guard, a concurrently changed state, or the reader limit. Do not spin; defer the work to a later pass.
Compile error for an ordering, compare-exchange, or guard on an Apple GPU Apple devices support only relaxed or acquire loads, relaxed or release stores, and relaxed add and subtract. Use per-particle output instead.
Compile error when an AtomicView or SyncView is in a resource or capture Views do not transfer to kernels. Use per-particle output, or a mutable adapter that manages its own atomic buffer.
Ordinary data written next to a relaxed counter is not visible Relaxed operations order nothing else. Use release stores and acquire loads to publish data.

Structural locks are not mutexes; neither are resource leases. The synchronization reference lists supported orderings per backend, guard rules, and device memory requirements.
