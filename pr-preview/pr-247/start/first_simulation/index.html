Your first simulation

In this tutorial you build a program that moves particles across a plane and checks where they end up. You define the particle data, write the movement logic once, and let Larecs apply it to every entity with the required components.

You need a working Mojo installation and the Larecs source, as described in Installation. The tutorial assumes you can read basic Mojo: structs, functions, and var declarations. See the Mojo manual for the language basics.

Describe particles with components

Section titled “Describe particles with components”

An entity is a particle’s identity: a handle with no data of its own. Components are the data you attach to an entity. A particle has a position and a velocity:

Components are ordinary structs. @fieldwise_init generates the constructor Position(x, y). Both structs conform to Larecs’s component.ComponentType constraint, which requires copyable, destructible values. Each component type appears at most once per entity.

Share the step length as a resource

Section titled “Share the step length as a resource”

Every particle moves for the same amount of simulated time per step. Data that exists once for the whole simulation, rather than once per entity, is a resource:

Time conforms to resource.ResourceType, the constraint for values stored as resources.

Write the movement kernel

Section titled “Write the movement kernel”

A kernel is a function that Larecs calls with a KernelContext. Iterating the context visits every entity that matches the kernel’s filter:

move_filter declares two things at compile time:

  • Which entities match. Only entities with both Position and Velocity are visited.
  • How the kernel accesses each component. include[Position]() grants read-write access, and read[Velocity]() grants read-only access. Larecs rejects writes to Velocity at compile time.

move_resources declares that the kernel reads Time. A kernel can access only the resources it declares.

ref binds a reference to the stored component, so assigning to position.x changes the stored component in place.

Run the kernel from a system

Section titled “Run the kernel from a system”

A system holds application logic and runs once per simulation step. Move runs the kernel:

Move implements the System trait. The scheduler calls its update method once per step and passes a SystemContext. SystemContext[...] lets the compiler infer the context’s parameters from the world it belongs to. [context.runmove](https://larecs.github.io/larecs/pr-preview/pr-247/larecs/system/SystemContext/#run) calls move for the particles that match move_filter.

System also offers initialize and finalize, which run once before the first and after the last step. Move keeps their default empty implementations.

Create the world

Section titled “Create the world”

A World stores all entities, components, and resources. Its parameters list every component type the world can hold:

add_entity creates an entity with the given components and returns its Entity handle. walker and climber have both components. marker has only a position, so move never visits it.

Run the scheduler

Section titled “Run the scheduler”

The Scheduler owns the world and calls your systems in the order you add them:

Scheduler[Position, Velocity] repeats the world’s component types because the scheduler’s type must match the world it owns. world^ transfers ownership of the world to the scheduler; world is no longer usable afterwards. run(steps=10) initializes every system, calls each update ten times, and finalizes every system.

Check the result

Section titled “Check the result”

After ten steps of 0.1, walker has moved one unit along x and climber two units along y. marker has not moved:

Read components back through scheduler.world.storage with the entity handles from add_entity. assert_almost_equal tolerates the rounding error of adding 0.1 ten times.

What happened in each step

Section titled “What happened in each step”

One context.run[move]() call. Larecs keeps entities with the same set of components together in one store. The filter decides which stores move sees: the store with Position and Velocity gets a KernelContext, and move visits its rows in order. The store without Velocity is skipped entirely.

On the host, context.run[move]() calls move once for each non-empty store that matches the filter, one after the other, and returns when all calls have finished. Write kernels so that each call handles only the rows of its own context; a world with more component combinations has more stores and therefore more calls per step.
