      Execution
      Run threaded host kernels

      Run threaded host kernels

      Split one particle movement call into chunks that run concurrently on host worker threads. Use this when a single kernel call covers many independent rows and profiling shows that the call dominates a step. Only the rows of one call are split; systems still run one after another in registration order. Threaded execution is experimental.

      Start with Update entities with systems and kernels.

      Move particles in threaded chunks

      The stage uses the portable particle model and the movement kernel from the first simulation.

      @fieldwise_init
struct Position(Copyable, Movable, TrivialRegisterPassable):
    """Particle coordinates, using device-compatible scalar arithmetic."""

    var x: Float32
    var y: Float32


@fieldwise_init
struct Velocity(Copyable, Movable, TrivialRegisterPassable):
    """Particle displacement per unit of simulated time."""

    var dx: Float32
    var dy: Float32


@fieldwise_init
struct Time(Copyable, Movable):
    """Shared simulated step length."""

    var delta: Float32
      comptime move_filter = Filter().include[Position]().read[Velocity]()
comptime move_resources = Resources().read[Time]()


def move(context: KernelContext[move_filter, move_resources]):
    """Moves each row using its velocity and the shared step length.

    Args:
        context: Matching rows and read-only time.
    """
    ref time = context.resources.get[Time]()
    for particle in context:
        ref position = particle.get[Position]()
        ref velocity = particle.get[Velocity]()
        position.x += velocity.dx * time.delta
        position.y += velocity.dy * time.delta

      move is a thin kernel: a named def function that run receives as a compile-time parameter, as in context.run[move](). It captures no local variables, which threaded execution requires. Each row writes only its own Position, so no two chunks write the same data. Resources().read[Time]() declares Time read-only, so all chunks share one immutable value.

      Opt in for one call with threaded=True:

      @fieldwise_init
struct Move[threaded: Bool](System):
    """Opts into host chunks for this movement kernel."""

    def update(mut self, mut context: SystemContext[...]) raises:
        """Moves disjoint rows and joins before returning.

        Args:
            context: Access to the simulation world.

        Raises:
            Error: If threaded eligibility or preparation fails.
        """
        context.run[move, threaded=Self.threaded]()

      Then give the world more than one worker:

      def run_stage[threaded: Bool](workers: Int) raises -> Position:
    """Checks parallel dispatch and whole-range fallback against exact values.

    Parameters:
        threaded: Whether to opt into the threaded engine.

    Args:
        workers: Submitted task budget; one exercises sequential fallback.

    Raises:
        Error: If configuration, execution, or a result check fails.

    Returns:
        Coordinate sums after two steps.
    """
    var world = World[Position, Velocity](
        execution_config=ThreadedExecutionConfig(
            workers=workers, chunks_per_worker=2, min_parallel_rows=0
        )
    )
    world.resources.add(Time(0.25))
    _ = world.storage.add_entities(Position(0, 0), Velocity(1, 2), count=4097)
    var scheduler = Scheduler[Position, Velocity](world^)
    scheduler.add_system(Move[threaded]())
    scheduler.run(steps=2)
    var total = Position(0, 0)
    for particle in scheduler.world.storage.query[move_filter]():
        ref position = particle.get[Position]()
        assert_almost_equal(position.x, 0.5)
        assert_almost_equal(position.y, 1.0)
        total.x += position.x
        total.y += position.y
    return total


def main() raises:
    """Compares the sequential, one-worker, and multi-task call paths.

    Raises:
        Error: If an execution path disagrees.
    """
    var sequential = run_stage[False](1)
    var fallback = run_stage[True](1)
    var threaded = run_stage[True](4)
    assert_equal(fallback.x, sequential.x)
    assert_equal(fallback.y, sequential.y)
    assert_equal(threaded.x, sequential.x)
    assert_equal(threaded.y, sequential.y)
    print(
        "PASS: sequential, one-worker fallback, and four-task particle parity"
    )

      ThreadedExecutionConfig sets the number of tasks Larecs submits per call, not reserved cores. chunks_per_worker=2 targets two chunks per worker, and min_parallel_rows=0 removes the row cutoff, so the 4097 particles split into chunks. The driver runs the same two steps three times, each in a fresh world: sequentially, threaded with one worker, and threaded with four workers.

      From the repository root, run:

      pixi run mojo run -I src examples/particles/threaded.mojo

      The program prints a PASS line when all three runs move every particle to (0.5, 1.0).

      How Larecs splits the rows

      Larecs splits each matching physical store into kernel chunks: contiguous row ranges, each passed to one kernel invocation. Workers claim chunks in an unspecified order, and run returns only after every chunk has finished. This changes what code outside the row loop sees:

      • Code before or after the for loop runs once per chunk, not once per store.
      • A row’s idx restarts at zero in each chunk; row indices are not entity IDs.
      • Work that reads rows of other chunks needs a later run, after this call returns.

      Work mapping explains how Larecs sizes chunks.

      Variations

      Keep small calls sequential

      The default configuration has one worker, four chunks per worker, and a cutoff of 65,536 matched rows. With one worker, or with fewer matched rows than min_parallel_rows, a threaded=True call runs sequentially, once per physical store. Keep threaded=True in the system and set the worker budget per world; the compile-time eligibility checks apply either way.

      Run threaded on a selection

      EntitySelection.run accepts the same threaded=True parameter and splits only the selection’s rows.

      Read an owning collection

      Ordinary resources in a threaded call must be read-only values without pointers or owned memory. To read a list or buffer, wrap it in an adapted resource.

      Failures and limits

      Failure Cause and fix
      Threaded components require pointer-free trivial plain values An accessed component holds a pointer or owns memory, such as a List. Remove it from the filter, or keep that data in an adapted resource.
      Threaded resources require explicit read access The kernel declares an ordinary resource as writable, including through the Resources[Time]() read-write default. Declare it with read, or write per-row output as in Coordinate shared writes.
      Compile error for a lexical closure, captures, or DEVICE Threaded execution requires a thin kernel without capture slots on ExecutionBackend.HOST.
      ThreadedExecutionConfig raises workers and chunks_per_worker must be positive, their product must fit in an Int, and min_parallel_rows must not be negative.
      Locked-world error or lock exhaustion Each threaded call takes one extra structural lock, even when it runs sequentially. Empty queries and selections hold locks; end them before the call.
      No speedup Dispatch costs time; measure complete steps before you change the cutoff.

      Chunks are independent only in the rows they visit. Structural locks are not mutexes: shared state still needs a race-free write strategy. The threaded execution reference lists the remaining lock, alias, and failure rules.
