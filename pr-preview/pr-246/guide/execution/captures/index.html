Pass local values to kernels

Give the particle kernel a step-local scale and get a particle count back, without storing either value as a world resource. Use a lexical closure when the kernel runs sequentially on the host, and explicit capture slots when the same kernel must also run on a device. Threaded execution accepts neither; pass its inputs through read-only resources or components.

Start with Execute on a device, which introduces the backend parameter. Run threaded host kernels defines thin kernels.

Borrow locals with a closure on the host

Section titled “Borrow locals with a closure on the host”

Both programs on this page use the portable particle model.

A lexical closure is a def nested inside another function that names the local variables it uses in a capture list. Here, move is defined inside Move.update and passed to run as a value:

The capture list {imm scale, mut visits} borrows scale read-only and visits mutably. context.run(move) selects the overload that takes a callable value; it runs only sequentially on the host. Larecs calls move once per matching physical store, and visits increases once per row. run returns after the last call, so the assertion sees the final count.

Declare explicit slots for a thin kernel

Section titled “Declare explicit slots for a thin kernel”

A thin kernel cannot borrow locals, but it can declare ordered capture slots with Captures. The system binds a local value to each slot when it calls run, on the host or on a device.

Slot 0 is a ReadCapture input; get[0]() returns its value. Slot 1 is a MutCapture output. Every invocation, and on a device every thread, sees the same output value, so only one writer may update it:

  • On the host, each invocation covers one physical store and adds its own row count, context.length. Sequential invocations never overlap.
  • On a device, one launch covers all rows. comptime if is_gpu() compiles the check only for the device, where only the thread with global index zero adds the packed row count.

This works because no thread reads another thread’s result. A thread-zero branch is not a barrier, and it does not make a general reduction safe.

Bind locals in the declared order when the system runs:

read_capture and mut_capture borrow scale and processed until run returns. On the host, the kernel uses the original values. On a device, Larecs uploads every binding on each call and copies the mutable slot back before run returns, so processed holds 37 at the assertion.

Variations

Section titled “Variations”

Keep a value between steps

Section titled “Keep a value between steps”

A capture lives for one run call. A value that persists between steps, or that owns memory, belongs in a resource or a portable resource.

Produce one result per particle

Section titled “Produce one result per particle”

When many invocations or threads contribute to a result, write a per-particle component and reduce it after run, as in Coordinate shared writes.

Failures and limits

Section titled “Failures and limits”
Failure Cause and fix
Compile error on the slot count, type, or mutability Bind one value per slot in declaration order, with the declared type. Two slots may share a type; their index distinguishes them.
Borrow-checker error on one local One local cannot be bound read-only and mutably in the same call. Use separate values.
Compile error for a device capture that owns memory or holds a pointer Device captures copy plain bytes. Use a portable resource for owning data.
Wrong result from several writers A mutable slot provides no synchronization. Use one writer, or per-particle output.
Compile error for a closure with DEVICE or threaded=True Lexical closures run only sequentially on the host. Use explicit slots for a device.

Keep references from capture slots and closure borrows inside the kernel; they must not outlive the call. The capture reference lists the remaining binding rules.
