# 1.0.0b3 todos

This is the carry-forward checklist for work left after the locked entity
selection API in 1.0.0b2. The completed implementation and its evidence remain
in [the selection plan](entity-selection-implementation-plan.md); the agreed
behavior remains in [the selection design](entity-selection-design.md). Check
items here only after recording the corresponding validation evidence.

## Finish entity selection internals and migration

Work in dependency order. Preserve in-place `EntitySelection.add`, `remove`, and
`replace`, context-manager lock ownership, ordinary queries, and low-level
storage operations. Do not expand the selection API as part of this cleanup.

- [ ] Extract shared CPU execution plumbing for full-world and selected ranges,
  including capture and resource binding. Keep full-world range discovery lazy;
  rerun ordinary system and query tests after the refactor.
- [ ] Share batch mutation internals between low-level storage operations and
  selections. Preserve the whole-archetype bulk fast path and exact partial-row
  behavior, rather than routing large batches through per-entity movement.
- [ ] Migrate remaining mutation-result callers to selections where they need
  selected execution. Keep low-level `HostStorage` callers usable through a
  documented adapter or return type; it cannot directly return a selection that
  borrows a full `World`.
- [ ] Replace `_WorldEntityIterator` query duties before removing that type and
  mutation-only `has_start_indices` machinery. Preserve query lock lifetime,
  iteration, and supported copy/move behavior.
- [ ] Update `test/world_entity_iterator_test.mojo`, `test/world_test.mojo`, and
  affected callers. Cover ordinary queries, low-level compatibility, batch
  mutation results, lock release, and selected mutation chains.

## Measure the refactor

`benchmark/entity_selection_benchmark.mojo` already covers full-world CPU
execution, small contiguous and disjoint selections in a 100k-entity world,
selected mutation chains, and a selected GPU case. Complete the comparison
rather than treating earlier overlapping validation runs as a baseline.

- [ ] Run matching workloads before and after the internal refactor, including
  ordinary full-world execution and existing large whole-archetype batch
  benchmarks. Use isolated checkouts at the relevant commits, the same Mojo
  environment and hardware, and sequential runs without concurrent compilation.
  Commit `bde4e08` is the pre-refactor reference; commit `691cbc4` is available
  locally if a pre-selection reference is also useful.
- [ ] Record workload sizes, commit IDs, Mojo version, hardware, run method,
  baseline and revised timings, and any regressions. Distinguish measured GPU
  execution from cases skipped because hardware is unavailable.
- [ ] Investigate material regressions before closing the migration checklist.

## Heap-backed GPU resources

This is separate from entity selection. The current GPU resource path copies
raw bytes and does not encode host heap ownership for the device. Keep its
existing type restrictions until a safe transfer model is implemented.

- [ ] Decide and document the ownership, encoding, lifetime, synchronization,
  and copy-back model for heap-backed resources on GPU.
- [ ] Implement and test `TileTensor` compatibility under that model.
- [ ] Resolve `Dict` compatibility and any `DevicePassable` conversion needed;
  verify unsupported types fail clearly.
- [ ] Update the GPU resource guides after the API and hardware tests are
  verified. Preserve the documented `ResourceStorage.get` `UnsafeAnyOrigin`
  contract unless Mojo can express the underlying ownership relationship.
